# Supplementary benchmark: dashboard queries and limits on the request path, 2026-10-17, `ef934dd`

**Supplementary run.** It measures the two NFR-01 items that the [ec9c440 benchmark](2026-10-17-ec9c440.md) left open:

- dashboard query latency (target p95 < 500 ms);
- Valkey on the request path.

It was measured with `RATES=100 VARIANTS=nonstream STEP_DURATION=5m LIMITS_STEP=1 DASHBOARD=1 load/run.sh` ([load/README.md](../../load/README.md#supplementary-steps)) on 2026-10-17, from 14:11 to 14:29 UTC, at commit `ef934dd`. That commit is `745a250` plus the `load/` changes that add these steps; the product code is the same as at `745a250`. Every number below was measured in this run (DoD #10).

## Result

- **Dashboard queries meet p95 < 500 ms on this dataset**, both on an idle stack and during 100 RPS of inference.
  - The slowest query is the usage report. Its p95 is 269–283 ms idle and 379–407 ms under load, and its maximum is 467–590 ms.
  - Every other query has p95 ≤ 127 ms.
  - The dataset is small: about 63 000 request rows from 20 minutes of traffic. Every query therefore read raw request rows. See [Dataset](#dataset): the result says nothing about a full day of traffic at this rate.
- **A Rate Limit and a Concurrency Limit add no measurable overhead at 100 RPS.**
  - With limits, overhead p95 is **4.5 ms** (Prometheus) / 3.5 ms (DB), with 0 errors.
  - The [ec9c440](2026-10-17-ec9c440.md) no-limits step at 100 RPS measured 4.4 ms / 3.5 ms.
  - The `modelswitch.limits` span, which includes the Valkey round trip, has p50 206 µs, p95 462 µs and p99 1.2 ms.
  - No metric times the limits decision. Its numbers come from trace spans sampled from Tempo.
- **The no-limits step of this run had a transient stall.** Its overhead p95 was 20.1 ms, with e2e max 2.9 s, 78 dropped iterations and the pool briefly at 40 of 40.
  - It was the first measured step on the fresh stack. I did not find the cause.
  - The comparison therefore also uses the ec9c440 run's 100 RPS step, which was measured the same way.

**Which rows were read.** A range of 24 h or less reads the raw `inference_request` rows. A longer range reads `usage_hourly` for whole hours and raw rows for the partial hours at the edges ([usage-and-budgets.md](../usage-and-budgets.md)).

- All the traffic falls inside one partial hour. So the 24 h queries (`overview_24h`, `usage_24h_by_alias`) read every raw row.
- The 7-day Overview and the month usage report found nothing in their whole-hour part, and read the same rows through the raw edge path.
- The rollup was fully caught up: 0 unpublished outbox events, and `usage_hourly` counts every request.
- **The rollup path for whole hours was therefore not exercised.** Raw-row queries over 24 h of sustained traffic (millions of rows at 100 RPS) were not measured either. The usage report's latency grew with the row count between the idle run and the run under load. Measuring a 24 h dataset needs a longer fill or a generated dataset, and is left open.

## Limits on the request path

Non-streaming, 100 RPS for 5 min each.

| Step | Achieved RPS | Errors | Dropped | Overhead p50 / p95 / p99, Prometheus (ms) | Overhead p50 / p95 / p99, DB (ms) | k6 e2e p50 / p95 / p99 (ms) |

| No limits (this run; transient stall) | 99.7 | 0 % | 78 | 2.2 / 20.1 / 212.8 | 1.8 / 16.5 / 209.8 | 208.7 / 256.1 / 725.6 |
| No limits ([ec9c440](2026-10-17-ec9c440.md), same method) | 99.9 | 0 % | 0 | 1.9 / 4.4 / 9.6 | 1.4 / 3.5 / 8.5 | 206.6 / 212.6 / 226.5 |
| **Rate and Concurrency Limit** | 99.9 | 0 % | 0 | 1.9 / **4.5** / 9.1 | 1.4 / 3.5 / 7.3 | 207.4 / 213.8 / 224.0 |

| Limits decision (`modelswitch.limits` span) | Sampled spans | p50 | p95 | p99 | Max |
|---|---|---|---|---|---|
| No limits: no Valkey call | 5 000 | 1.4 µs | 3.4 µs | 8.0 µs | 140 µs |
| Rate and Concurrency Limit: one Valkey round trip | 5 000 | 205.7 µs | 462.1 µs | 1 229.6 µs | 30.3 ms |

**What these numbers are.**

- **No Prometheus metric times the limits decision.** The step samples the `modelswitch.limits` span, which wraps the decision and its Valkey call, from Tempo in `otel-lgtm`. Tempo's search returned 5 000 traces per step, out of about 30 000, and the script kept those that started inside the step. The sample is whatever Tempo returned, not a random draw.
- **Valkey's own time, from `INFO commandstats` over the limits step:**
  - 30 000 `EVALSHA` calls, at 50.8 µs each. That is one per request, and the time includes the commands the script runs.
  - 30 000 each of `TIME`, `ZADD`, `ZREM`, `GET`, `SET`, `ZCARD`, `PEXPIRE` and `ZREMRANGEBYSCORE`, at 0.3–4.5 µs each.
  - So most of the roughly 200–460 µs the api waits is the network round trip and client-side scheduling, not time inside Valkey.
- **The limits step did not use the database pool much.** At most 2 connections were in use, with DB operation p95 1.0 ms. In the stalled no-limits step, the pool reached 40.
- **The release path is not timed separately.** It happens after the response, outside `modelswitch.limits`.

## Limitations

- **Small dataset.** It holds about 63 000–81 000 requests, all inside one hour. The rollup path for whole hours was not exercised, and nothing measures a full day of traffic. NFR-01 asks for the dashboard target "on the benchmark dataset", and this is the only dataset measured so far.
- **Dashboard concurrency is modest:** 9 queries per second, about one per second per query, from one Owner session. Many concurrent dashboard users were not measured.
- **k6 end-to-end timing** includes Docker Desktop's port forwarder and Caddy. Server-side query time was not isolated.
- **Limits timing comes from sampled trace spans.** It relies on trace sampling at 1.0, which a production deployment may lower.
- **The no-limits step of this run stalled for a short time,** cause not found. The limits comparison therefore leans on the ec9c440 step.
- **Laptop hardware.** The 4-CPU / 3.8 GiB Docker VM is shared with `otel-lgtm`. The 200 ms Mock Provider sends tiny bodies.
