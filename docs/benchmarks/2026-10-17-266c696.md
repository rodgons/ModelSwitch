# Gateway overhead benchmark: 2026-10-17, `266c696`

Measured with `load/run.sh` ([load/README.md](../../load/README.md)) on 2026-10-17, from 08:08 to 08:53 UTC, at commit `266c696`. Target: NFR-01, gateway overhead p95 < 100 ms. Every number below was measured in this run (DoD #10). Nothing is extrapolated.

## Result

- **NFR-01 is met at 50 RPS and missed from 100 RPS up.** The setup is a single Tenant, a 200 ms Mock Provider, and a 4-CPU / 4 GB Docker VM on a laptop.
  - At 50 RPS the overhead p95 is **4.9 ms** non-streaming and **8.8 ms** streaming, with no errors.
  - At 100 RPS the median overhead stays at about 2 ms. The tail breaks: non-streaming p95 is **159 ms** with 4.7 % errors, streaming p95 is **66 ms** with 2.9 % errors.
  - At 200 and 400 RPS the stack saturates: 79–89 % of requests fail, and overhead is measured in seconds.
- **The bottleneck is the database path, not CPU in the gateway.** Every request updates its Tenant's `usage.budget_period` row twice, once when it reserves and once when it settles ([usage-and-budgets.md §3](../usage-and-budgets.md#3-budget-enforcement-reservation-model)). This happens even for a Tenant with no Budget.
  - Both updates run inside multi-statement transactions. The row lock is held across several client round trips, until commit.
  - With one Tenant, every request queues on one row lock. A `pg_stat_activity` snapshot at the start of the 200 RPS step showed 83 sessions in `Lock:transactionid` on `budget_period` statements.
  - Each waiting request holds a pooled connection, so the api's Npgsql pool reaches its 100-connection maximum.
  - PostgreSQL's `max_connections` is also 100, and the worker holds connections too. PostgreSQL then refuses new clients ("sorry, too many clients already"), and those requests fail with HTTP 500.
- **A diagnostic run with 16 Tenants confirms the lock contention** ([below](#diagnostic-16-tenants)): 100 RPS ran clean, with p95 7.7 ms and 0 errors. The stack still saturated at about 135 RPS achieved, with lock waits on `budget_period` again and PostgreSQL at about 1.8 cores.
- The api never used more than about 1.5 cores of the 4. GC pauses were not the cause (see [Resources](#resources)).

How to read the table:

- **Errors** are k6 requests without a 200 status and a complete body.
- **Dropped** counts the iterations k6 could not start because every VU was busy.
- **Overhead percentiles cover only requests the gateway recorded.** A request whose Reservation could not open a connection was answered with HTTP 500 from an unhandled `Npgsql.PostgresException` (`http_server_request_duration` by `error_type`). It was not counted in `modelswitch.inference.requests` or in the overhead histogram, and it has no `inference_request` row. Under saturation the overhead columns therefore describe the survivors. The Errors and k6 columns describe all requests. This metric gap is listed under [Findings](#findings).
- The Prometheus and DB columns agree closely below saturation. The DB column has whole-millisecond resolution, because `duration_ms` is an integer. The Prometheus column is interpolated between bucket bounds (25, 50, 75, 100, 250 ms…).
- At 50 RPS, e2e − mock (p95 15.6 ms) is about 11 ms above the server-side p95. That difference is the path outside the api: the Docker Desktop port forwarder, Caddy and k6.

## Diagnostic: 16 Tenants

This run was not part of the standard benchmark. It used `TENANTS=16 VARIANTS=nonstream RATES=100,200,400 STEP_DURATION=2m load/run.sh` on the same machine (also otherwise idle), right after the main run, on a fresh stack. Each request used a random key out of 16 Tenants, so `budget_period` updates are spread over 16 rows.

Spreading the load over 16 Tenants moves the 100 RPS step from a missed target (p95 159 ms, 4.7 % errors) to a comfortable pass (p95 7.7 ms, 0 errors, at most 8 connections in use). The ceiling is still about 135 RPS.

Right after the 200 RPS step, while its backlog drained, `pg_stat_activity` showed 40 sessions waiting on `Lock:transactionid` for `budget_period` statements. It also showed 27 sessions `idle in transaction` in the middle of the Reserve and Settle transactions, waiting on the api's next round trip. The row lock is held across those round trips. Under CPU pressure each round trip takes longer, so the lock is held longer and more requests pile up behind it. PostgreSQL used about 1.6–1.8 cores and the api about 1.1–1.2 cores. The outbox lag grew to 105–259 s.

## Findings

These are follow-ups. Code was not tuned for this report.

1. **Per-Tenant hot row.** `budget_period` is updated on every request, even without a Budget, and the row lock is held across the rest of the Reserve and Settle transactions. Possible directions, not yet evaluated:
   - make the `budget_period` statement the last one before commit, so the lock is held for one round trip;
   - skip the period row for Tenants without a Budget;
   - batch the `spent_amount` updates.
2. **Pool size versus `max_connections`.** The api's Npgsql pool (default `Max Pool Size` = 100), the worker's pools and the LISTEN connection together exceed PostgreSQL's default `max_connections` = 100. Under pressure PostgreSQL refuses connections instead of the pool queueing them, so requests fail with 500 instead of waiting. The Compose deployment should cap the pool below `max_connections` (or raise `max_connections`), and [deployment.md](../deployment.md) should say so.
3. **Unrecorded failures.** A request that fails with an unhandled database exception before its Reservation exists is counted in no `modelswitch.*` metric. It is visible only in ASP.NET Core's `http.server.request.duration` with `error_type`. The error also should not reach the client as a bare 500: it should map to a code in the closed set of [api.md §2](../api.md).
4. **Log volume.** No `Logging` section is configured, so EF Core logs every DB command and `HttpClient` logs four lines per Provider call at Information level. That is about ten JSON log lines per request, written to the console and exported over OTLP. This did not cause the saturation (the api stayed under 1.6 cores), but it adds cost to every request.

## Limitations

- **Laptop hardware.** The Docker VM has 4 CPUs and 3.8 GiB, and runs the whole stack plus `otel-lgtm` (Grafana, Prometheus, Tempo, Loki), which used up to 1.7 GiB and up to about 1 core. k6 ran on the macOS host and used host cores outside the VM. Requests crossed Docker Desktop's port forwarder, which the server-side metric excludes but the k6 numbers include.
- **Single api replica, single Tenant.** The standard workload uses one Tenant, which is the worst case for the per-Tenant `budget_period` row. Real multi-tenant traffic spreads that contention, as the 16-Tenant diagnostic shows, but still saturated at about 135 RPS here.
- **Sequential steps on one stack.** After a saturated step, the next step starts on a stack that may still be draining: requests left `running`, Reservations waiting for the sweeper, and outbox lag. The 400 RPS steps and the first streaming step are affected. The 32 s gap is not enough to drain fully, as the outbox lag of 127 s at the end of the 400 RPS step shows.
- **Overhead percentiles under saturation** cover only requests the gateway recorded (see [Gateway overhead](#gateway-overhead)). The Prometheus percentiles are interpolated within histogram buckets. The DB percentiles are exact to 1 ms.
- **Not measured:** Npgsql pool wait time (no instrument; pool exhaustion is shown instead), Valkey latency on the request path (not exercised without limits), and GC by generation.
- **Trace sampling** was 1.0 and log levels were the defaults. A production deployment would likely sample traces and raise log levels, which would lower the per-request cost. No such tuning was applied.
- **Mock Provider.** The mock answers after exactly 200 ms with a tiny body. Real Providers send larger bodies and more stream chunks.
