# Admin Dashboard (Frontend)

This document covers PRD §9. The dashboard is an administrative tool, not a chat UI. The UI is English-only in the MVP: strings live in components, with no i18n layer.

## 1. Stack and structure

Vue 3 (`<script setup>`, Composition API) + TypeScript (strict) + Vite. Vue Router, Pinia (session/UI state only), TanStack Query for Vue (all server state), StyleX for styling (constitution, *Stack*), PrimeVue 4 (unstyled mode, styled through pass-through classes from the token layer in [design-system.md](design-system.md)) for dialogs, ECharts via `vue-echarts` for charts. Tables are native `<table>` elements and form controls native `<input>`/`<select>` with `<label>`s, which are accessible as they are. The API client is generated from `/openapi/v1.json` with `openapi-typescript` and called through `openapi-fetch`. Generated types are committed: `web/openapi.json` is checked against the served document by `OpenApiDocumentTests` (rewrite it with `UPDATE_OPENAPI=1`), and `pnpm check:api` fails if regenerating `src/api/schema.d.ts` produces a diff.

**Styles.** `stylex.create` calls live in `*.styles.ts` modules next to the components (and tokens in `shared/design/*.stylex.ts`), not in `.vue` files; templates apply them with `v-bind="stylex.props(...)"`. `app/global.css` holds only a box-sizing reset, and the StyleX plugin appends the compiled rules to it. Fonts are served from `web/public/fonts/` (SIL OFL). Chart colors are the one place outside the token files with hex values (`shared/design/chart.ts`), because canvas charts need concrete colors.

**Development.** `pnpm dev` serves the dashboard on `http://localhost:5173` and proxies `/admin`, `/v1`, `/health`, `/ready` and `/openapi` to the api, so the browser sees one origin (ADR-0011). The api must be reached over HTTPS, because its `__Host-` cookies and antiforgery require it: run it with `ASPNETCORE_URLS=https://localhost:5081` and the ASP.NET development certificate (`dotnet dev-certs https`); the proxy accepts that certificate. `MODELSWITCH_API_URL` overrides the target.

```
web/src/
  api/            # generated schema.d.ts + typed client + query keys
  app/            # router, layout, auth guard, error boundary
  features/
    overview/ requests/ providers/ routing/ tenants/ evaluations/ admin/
      components/  pages/  queries.ts
  shared/
    design/       # StyleX tokens and themes (design-system.md §1)
    layout/       # AppShell, Container, Stack, Inline, Grid, Split, Panel… (design-system.md §9)
    components/   # DataTable wrapper, EmptyState, ErrorState, Money, Tokens, Duration, EstimatedBadge
    format/       # the ONLY place units are formatted
```

| `/` Overview | Time-range picker (1 h, 24 h, 7 d, 30 d, custom); a `Readout` band (design-system.md §9.2): requests, success %, Estimated Cost, tokens, p50/p95 latency, p50/p95 TTFT, fallback %; time-series charts; recent failed requests with a mini Route Strip | Viewer |

| `/providers` | Provider list + health; create/edit, write-only secret field, connectivity test button with result | Owner (write) |

| `/evaluations` | A `SegmentedControl` for Datasets, Prompts and Comparisons, and a Tenant filter (every Tenant in the grant by default); both live in the URL query string (`?tab=`, `?tenantId=`). Datasets and Prompts are cursor-paginated tables (name, Tenant, task kind, latest version, created) with a create dialog (name, Tenant, and task kind for a Dataset) that opens the new item. The Comparisons tab lists Comparisons newest first, one row per run (target, Evaluator, status badge, Cases done of total, quality), filtered by Dataset and run status, and polls every 2 s while any run on the page is queued or running; its header action is **Start a run** | Viewer (Operator to write) |
| `/evaluations/datasets/:id` | Dataset facts, its Dataset Versions (version, Case count, content SHA-256, created) and an **upload** form: a `.jsonl` file picker, checked in the browser (extension, not empty, ≤ 10 MiB) before sending. The file is the raw request body (`Content-Type: application/x-ndjson`), sent through the typed client with a pass-through `bodySerializer` so the antiforgery header and Problem Details handling still apply. A 400 `validation_failed` lists the `errors` extension by 1-based line number (`lines[N]`, `lines[N].<field>`), with `body` errors first. A successful upload opens the new version. **Delete dataset** (Operators) opens a confirm dialog that names what goes with it and needs the Dataset's name typed; a 409 (a Comparison still uses it) stays in the dialog, and success returns to the Datasets tab | Viewer (Operator to upload or delete) |
| `/evaluations/datasets/:id/versions/:version` | Case count, content SHA-256 (copyable), the scoring schema as JSON, and the Cases in upload order, cursor-paginated: ordinal, Case id (`externalId`), and `input`, `expected` and `metadata` as one-line JSON cut to 60 characters, with a per-row Expand that shows each value pretty-printed. **Start a run** opens the builder on this version | Viewer |
| `/evaluations/prompts/:id` | Prompt facts, its Prompt Versions (aside) and the selected version (`?version=`, latest by default): each message with its role, the detected `{{variables}}` and the response format. **Create version** opens the messages editor pre-filled from the version shown: role select (system, user, assistant) and content per message, add, remove and move up or down, the detected variables (same identifier rule as the server's placeholder), and an optional response format checked as a JSON object before sending. Server errors land on their message (`messages[i].role`, `messages[i].content`, 0-based) or on the response format (`responseFormat`, `responseFormat.<field>`). **Delete prompt** works like Delete dataset (409 while a Comparison has a run built from it) | Viewer (Operator to write) |
| `/evaluations/new` | Run builder (`?tenantId=`, `?datasetId=`, `?version=` prefill it): Tenant, Dataset and version, Comparison name, concurrency, cost cap per run, and 1–6 Run Configurations (add, duplicate, remove). Each has a target (Model Alias from the Routing Policies, or a pinned Provider Model), a Prompt and version (latest by default), parameters (temperature, top P, seed, max output tokens) and an Evaluator restricted to the kinds that fit the task kind, with a form per kind (exact_match case folding; classification labels and json_fields fields prefilled from the version's `scoringSchema`; json_fields default and per-field comparators with tolerance; llm_judge judge alias, rubric and the model-judged note; pass threshold) and a JSON view that starts from the form. The **worst-case Estimated Cost** comes from `POST /admin/evaluations/estimate`, called 600 ms after the last change once every reference is chosen (late answers are dropped): total, per configuration worst case, judge share, "over the cost cap" and the Cases that would fail by error code. Malformed numbers and JSON are caught before sending under the server's keys; server errors (`configurations[i].…`, including `evaluator.config.labels[1]`) land on the matching field, and on success the new Comparison opens | Operator |
| `/evaluations/runs/:runId` | One run: status and progress, aggregates (quality, errored rate, pass/fail/errored/skipped counts, latency, candidate/judge/total Estimated Cost, tokens; labelled live while unfinished), the reproducibility record (target, Dataset Version and content hash, Prompt Version, Evaluator, config hash, gateway version, times, cost cap), failures by status and error code, the frozen Run Configuration, and Case Results filtered by status and cursor-paginated, each linking to its request and to the Case drill-down. Export CSV/JSONL, and for Operators Cancel (while queued or running), Run again and Recompute aggregates (once finished). Polls every 2 s while unfinished | Viewer (Operator to act) |
| `/comparisons/:id` | Side-by-side table, one row per run numbered in configuration order (target, Prompt and Evaluator versions, a Model-judged badge for llm_judge, status with Cases done, quality with its metric and the run-to-run variance when the configuration has run at least twice, errored %, p50/p95 latency, and Estimated Cost per Case, candidate, judge and total, each column with the Estimated badge), with Details, CSV and JSONL export, Cancel and Run again per run. A note that LLM outputs are non-deterministic even at temperature 0. A quality-vs-per-Case-candidate-cost scatter (`ScatterChart`, ECharts, "View as table"). Per-run kind metrics from each run's aggregates: per-class precision/recall/F1/support, macro-F1 and the confusion matrix (classification), per-field accuracy and parse failure rate (json_fields), the judge score distribution (llm_judge). **Case drill-down**: enter a Case id (`?case=` fills it in and shows it) and each run is asked for that one Case's result (`externalId` filter, one request per run) to see each run's status, error code, score, prediction, latency, tokens, Estimated Cost, output and request links side by side, and a diff of two runs' outputs (JSON compared field by field with sorted keys, prose word by word). Polls every 2 s while any run is queued or running. **Delete comparison** works like Delete dataset: it removes the runs and every Case Result, outputs included, and is refused (409, shown in the dialog) while a run is queued, running or still stopping | Viewer (Operator to act) |
| `/admin` | Administrators, audit records | Owner |

## 3. UX rules

- **Units**: durations in ms below 1 s and s with 2 decimals above. Tokens use thousands separators (`12,480`). Money is in USD, with 4 significant decimals below $1 and 2 above. Formatting happens only through `shared/format`.
- **"Estimated" is never omitted** next to a cost. `<Money>` requires an `estimated` prop with no default, so the type system enforces this (PRD §9 UX).
- Every query-driven view handles four states: loading (skeleton), error (message + request id + retry), empty (explanation + next action), and data.
- Accessibility: every input has a `<label>`, tables are real `<table>` elements, focus is visible, dialogs trap focus, and charts have a data-table alternative ("View as table"). The Playwright smoke suite runs `axe-core`.
- Layouts are designed for desktop ≥ 1280 px and tablet ≥ 768 px (PRD §9). Phone is not a target, but nothing scrolls the page horizontally below 768 px ([design-system.md §9](design-system.md#9-responsive-behavior-and-primitives)).
- Visual rules (tokens, type, spacing, buttons, links, layout primitives) are in [design-system.md](design-system.md). Components never use raw colors, sizes or spacing.
- Secrets are never shown after they are submitted (PRD §9.3). A secret field shows only "configured · replace".
